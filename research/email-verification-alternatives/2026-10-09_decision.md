# Alternatif SMTP untuk verifikasi email DOVA

*Generated: 2026-10-09 | Routed: research → deep-research | Scope: DOVA customer registration/password reset*

## TL;DR

Untuk masalah Gmail yang dibatasi, pilihan paling cepat adalah memakai jalur HTTP Resend yang sudah ada di DOVA. Kode saat ini sudah memilih Resend bila `RESEND_API_KEY` dan `EMAIL_FROM` tersedia, selama kredensial SMTP tidak aktif. Jadi tahap pertama tidak membutuhkan perubahan flow OTP.

Jika volume Resend Free tidak cukup, pilihan berikutnya adalah menambah adapter HTTP provider transactional lain: SES untuk biaya dan scale, Brevo untuk API + opsi SMS/WhatsApp, atau Postmark untuk fokus transactional email. Semua provider tetap punya quota, sender/domain verification, dan reputasi; “non-SMTP” bukan berarti tanpa limit. Google sendiri mendesain Gmail dengan batas pengiriman dan perlindungan anti-spam, sehingga mailbox Gmail memang bukan fondasi ideal untuk transactional email ([source 07](sources/07_google_gmail_limits.md)).

## Temuan teknis dari DOVA

Flow saat ini sudah menangani OTP secara lokal: code dibuat dan di-hash, TTL/attempt/resend disimpan melalui Redis atau database, lalu `NotificationService` memanggil `sendEmail()`. Karena verifikasi code tidak bergantung pada provider, provider hanya perlu mengirim pesan; ini memudahkan penggantian provider.

Adapter sekarang mendukung SMTP dan Resend HTTP. Pemilihan SMTP terjadi bila `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, dan `EMAIL_FROM` ada. Selain kondisi itu, `sendEmail()` memanggil Resend API. Bukti lokal ini ada di `apps/backend/src/mail.util.ts`; lihat [source 01](sources/01_dova-current-http-resend.md).

## Hipotesis dan status

### H1 — DOVA bisa pindah dari Gmail SMTP dengan perubahan minimal

**Confirmed.** Adapter Resend HTTP sudah ada dan `sendEmail()` memilihnya ketika SMTP tidak terkonfigurasi. Resend menyediakan endpoint API untuk pengiriman email dan pricing saat ini mencantumkan Free 3.000 email/bulan dengan 100/hari serta Pro 50.000/bulan tanpa daily limit ([source 01](sources/01_dova-current-http-resend.md), [source 02](sources/02_resend_api_and_pricing.md)).

### H2 — Provider API transactional lebih cocok, tetapi tetap terbatas

**Confirmed.** Resend mencantumkan limit plan; Brevo mengembalikan `429` ketika rate limit terlampaui; Postmark dan Brevo mewajibkan autentikasi API; provider tetap mengatur sender/domain dan rate limits ([source 02](sources/02_resend_api_and_pricing.md), [source 03](sources/03_brevo_api.md), [source 05](sources/05_postmark_api.md)).

### H3 — SES paling ekonomis untuk scale, tetapi lebih berat dioperasikan

**Supported with caveat.** SES menyediakan `SendEmail` API dan quota yang bisa dinaikkan, tetapi akun sandbox dimulai dengan 200 email/24 jam dan 1 email/detik serta memerlukan verifikasi recipient. Ini membuat SES kuat untuk biaya/scale setelah production access dan reputasi siap, bukan necessarily jalur tercepat ([source 04](sources/04_aws_ses_api.md)).

### H4 — Kanal non-email dapat menghilangkan ketergantungan pada Gmail

**Confirmed, but not equivalent.** Twilio Verify mendukung SMS, WhatsApp, voice, email, TOTP, passkey, dan push. Namun email Verify memerlukan SendGrid integration; SMS/WhatsApp menambah biaya, nomor telepon, dan kebutuhan compliance. Ini adalah perubahan produk, bukan sekadar penggantian transport ([source 06](sources/06_twilio_verify_channels.md)).

## Rekomendasi keputusan

1. **Sekarang:** gunakan Resend HTTP adapter yang sudah ada. Buat subdomain transactional terpisah, misalnya `notify.dova...`, verifikasi domain/sender, dan isi `RESEND_API_KEY` + `EMAIL_FROM`. Pastikan variabel SMTP Gmail tidak ikut aktif karena adapter akan memilih SMTP bila kredensialnya lengkap.
2. **Sebelum production:** tambahkan metrik provider success/failure, provider response ID, retry terbatas dengan backoff, dan rate-limit per email/IP. Jangan retry otomatis tanpa batas karena bisa menggandakan OTP.
3. **Jika Resend quota tidak cukup:** tambahkan interface provider (`EmailTransport`) dan implementasi Brevo atau SES di balik interface. Jangan menaruh logic OTP di provider adapter.
4. **Jika email deliverability masih bermasalah:** tambahkan fallback SMS/WhatsApp melalui Twilio Verify atau provider regional setelah mengukur biaya dan coverage pengguna DOVA.

## Konfigurasi minimal yang disarankan

```env
EMAIL_FROM="DOVA <no-reply@transactional.example.com>"
RESEND_API_KEY=re_...
# kosongkan/nonaktifkan SMTP_HOST, SMTP_USER, SMTP_PASS agar jalur Resend dipilih
```

Verifikasi DNS SPF/DKIM/DMARC sesuai instruksi provider. Jangan commit API key. Untuk staging, pakai domain/subdomain terpisah dan alamat QA tetap yang diizinkan bila provider masih sandbox.

## Risiko dan acceptance criteria

- **Quota:** daily/monthly send failures < 0.5% pada target volume; alert saat 70% dan 90% quota.
- **Reliability:** `send-registration-code` mengembalikan success hanya ketika provider menerima request; retry maksimum 1 kali untuk error transient.
- **Security:** OTP tetap hanya disimpan sebagai hash, TTL/attempt lock tetap aktif, dan API key hanya server-side.
- **Deliverability:** SPF/DKIM/DMARC aktif; pantau bounce/complaint dan jangan mengirim ulang ke alamat yang bounce.
- **Fallback:** jika provider gagal, user mendapat pesan generik dan dapat resend setelah cooldown; jangan bocorkan apakah email terdaftar.
